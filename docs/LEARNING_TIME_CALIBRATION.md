# Per-user learning time calibration V2

## Current status

This is an additive pilot for the existing Neon + Supabase Auth + Workers application. GPT/MCP plugin changes are omitted per user direction; the Web App and budget backend share one server-side cost profile. The implementation preserves `attempts`, `fsrs_review_logs`, `user_words`, BKT evidence and Tutor Policy records. Timing observations are stored separately and cannot set an answer, rating, due date or evidence outcome.

Production was audited read-only on 2026-10-13. Neon reported 4 user profiles, 2,784 attempts, 1,061 submission events, 65 study sessions and 1,008 estimated budget events. Only one account had attempts. Every one of its 2,784 `active_ms` values was NULL (0% coverage); 410 attempts had `grading_ms` (14.7% of attempts). There were no historical feedback-time fields. Every activity/scope/first-attempt correctness group therefore had zero valid active-time observations; P50, P75, P90, mean, variance, answer-vs-feedback, and correct-vs-incorrect active-time differences are undefined. The missing times were not reconstructed from submission gaps. Estimated budget events are not ground truth because they come from the existing estimator.

The existing submit handlers explicitly pass `active_ms: null`; `grading_ms` measures the grading call only. A 14-day rolling backtest and selection among P50/P75/trimmed mean/EWMA/shrinkage cannot be done without observed answer or feedback durations. No model-winning MAE, bias, P75 error or budget-overrun claim is made.

CodeBuddy CLI was available and authenticated. Codex invoked its non-interactive review mode with tools disabled and supplied only anonymous counts (no answers, emails, identifiers, or credentials). CodeBuddy independently confirmed that zero valid observations cannot select an estimator, warned that a tiny-sample empirical P90 is unstable, and recommended a fixed domain cap and a time-ordered future evaluation. Its full note is in `docs/qa/time-calibration/codebuddy-statistics.md`. CodeBuddy did not access Neon and did not change files or data.

## Collection and isolation

The Worker issues the current session, phase, question index, retry, stage, phase start, user-local date and time zone to the Web App. The browser uses `performance.now()`. It pauses while hidden, while an answer or telemetry request is in flight, and after 30 seconds without activity. It checkpoints on phase entry and every 15 seconds. Refresh recovery uses session storage; the database merges retries and devices under an authenticated user-scoped task key and keeps the largest cumulative duration. Finalization after a successful phase transition must reuse a previously validated checkpoint for that exact phase, cursor, stage and start time. The server freezes activity and scope at the first checkpoint, so a transition cannot relabel answer time as feedback time. Closed sessions can finalize existing checkpoints; arbitrary stale phases cannot create them.

At local midnight, the timer splits active time at the learner's timezone boundary. It finalizes the prior-day segment with a rollover marker and starts a new segment for today. The SQL function accepts only the immediately previous local day, only for finalization, and caps the segment at that day's boundary. On reload, a prior-day segment for the same session is recovered from session storage. A missing checkpoint or browser storage can still lose the uncheckpointed fragment; no wall-clock gap is filled in.

Durations below 250 ms and above 300 seconds are recorded only as anomaly counts. Submitted chunks are capped at 600 seconds and the SQL function bounds a reported cumulative value by the server-observed phase age and prior checkpoint interval. Client timing remains an estimate, not trusted evidence. Grading/network waits do not enter the active timer. Feedback and explanation are distinct stages. A telemetry error is swallowed and does not block formal submission.

Neon migration `0006_learning_time_calibration_v2.sql` adds:

* `user_learning_time_observations`, keyed by authenticated user and stable task key for retry-safe checkpoints;
* `user_learning_time_daily`, keyed by user, local date, activity, scope, stage and model version, with sample counts, totals, 5-second histogram bins and anomaly counts;
* `user_learning_time_word_lifecycle`, keyed by the user's normalized canonical word, containing a single completed Pretest-to-Lesson cost sample plus an optional once-per-word share of completed group Consolidation;
* `record_learning_time_v2` and `user_learning_time_profile_v2`, which compare the supplied subject with the externally authenticated Neon subject and only aggregate one user's compact summaries.

The production database was not migrated. The final SQL revision was applied to isolated Neon branch `time-cal-v2-final-20261013` (`br-green-fire-azuy0fc1`), forked from production `main`; all three tables, both functions, RLS and three owner policies were verified there. No learning rows were added. PGlite tests exercise the migration with two user fixtures and verify idempotent aggregation, stale/future/long-time rejection, user mismatch rejection, rollover attribution, consolidation allocation and unchanged attempts. The repository's `check:db` script checks legacy business tables through Supabase, so it was not used as a Neon check; the migration was checked directly on the isolated Neon branch. Additive migration rollback is an application rollback plus retaining the unused tables/functions; do not remove real timing evidence after collection.

## Cost model and current limitations

`getUserLearningCostProfile(userId)` is the common server entry point used by Web budget calculation. The caller's authenticated user ID is the partition key; a bounded per-DB-client cache lives for 60 seconds. The profile exposes model version, activity/scope estimates, sample count, confidence, source and latest update time. If the flag is off or the query fails, the existing static costs are returned.

The pilot estimator combines matching personal histogram samples with the existing static activity cost using `w=n/(n+20)`, clips observations to three times the static cost, and falls back to personal related activity only when there are no exact samples. The histogram statistic is a capped mean with 5-second buckets, not P50, P75, trimmed mean or EWMA. The prior weight `k=20` is a provisional safety choice, not a backtest result. An observation can move an estimate gradually; fewer than 30 samples are marked low confidence. There are no pooled cross-user observations.

Review and individual activity estimates can become personal as valid samples arrive. The complete new-word estimate starts at the legacy 77 seconds and gradually adapts from per-user canonical-word lifecycles. A base sample is created only when one study session has valid Pretest, Lesson answer and Lesson feedback observations for the same normalized word and the Lesson advances or completes. One unique lifecycle row per user/word prevents another book label or later practice from counting it again. The base includes valid Pretest and Lesson answer, explanation and feedback segments. When a tracked group Consolidation completes, its valid answer and feedback time is divided across its unique canonical target words and added once to those lifecycle rows; the daily histogram moves each sample into its updated complete-path bucket. The separate Consolidation task estimate remains available for reserving that group task's budget. The cost profile exposes sample count and confidence, and returns 77 seconds when no completed lifecycle exists.

There is no historical calibration error series yet. On future records, compare fixed cost, personal mean, capped histogram mean and shrinkage using expanding-window folds; only timestamps before a prediction may train it. Report MAE, signed bias, P75 absolute error, budget overruns and coverage by user/session and activity. Do not fit or choose `k` until valid samples support those folds. Never treat `grading_ms`, session duration or budget reservations as answer-time truth.

## CPU, activation and rollback

Cloudflare's current Workers Free limit is 10 ms CPU per HTTP request ([official limit](https://developers.cloudflare.com/workers/platform/limits/)). The code uses compact database aggregates and a 60-second bounded profile cache; it does not scan `attempts` in a request, invoke an LLM, or simulate FSRS. Database/network wait is excluded from Workers CPU. A preview invocation has not been deployed, so no CPU P50/P95/P99, Neon latency, or end-to-end timing is claimed. The new migration and timer have local/PGlite tests only.

`WORDLOOP_TIME_CALIBRATION_V2` is the opt-in feature flag and is false in the checked-in config. With it disabled, the existing static model remains active. Rollback by setting the flag to `false` and deploying the prior-compatible Worker; retain additive timing data and schema. No production migration or Worker deployment occurred for this task.

## Independent review

CodeBuddy's statistical review completed using anonymous database aggregates only. An earlier pilot source review identified stale-finalization fabrication, missing consolidation collection, stage attribution and local-date risks; the Web path now requires matching checkpoints, tracks completed group consolidation, sends the phase stage, and splits the timer at the learner's midnight. Those corrections are covered by the current SQL/browser tests. The final-source-review requests in CodeBuddy print mode returned unexecuted tool-call scaffolding instead of a report, so this commit does not claim a final independent CodeBuddy source review. MCP-specific comments were out of scope after the user asked to omit the plugin. No test or simulated log result is represented as an actual user outcome.
