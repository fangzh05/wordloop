# Adaptive daily study budget V2

WordLoop plans study from the learner's daily time budget. The default remains 45 minutes in the learner's local day (Asia/Shanghai by default). `daily_new_word_limit` is a safety ceiling, not a quota: new learners receive a ceiling of 20, while migration leaves each existing learner's configured value intact. The backend computes an adaptive cumulative target from remaining time, due reviews, personalized costs and the projected future review load. Web Today, Study and Insights use the same authenticated backend plan. GPT/MCP UI work is omitted; its learning-state boundary remains unchanged.

## Controller and admission

`server/services/adaptiveDailyBudget.ts` is a pure, deterministic planner. `learning_budget_snapshot_v1` provides one compact, user-scoped Neon snapshot; `getLearningBudget` combines it with `getUserLearningCostProfile` and runs the planner at planning/bootstrap boundaries. The planner:

1. Reserves a 5% time buffer, clamped to 60–180 seconds. The snapshot uses the larger of measured effective time and idempotent task reservations; it also excludes a same-day frozen Review from the outstanding due estimate, so that work is not charged twice.
2. Prices remaining due and overdue reviews before new words. If they consume the usable capacity, the new-word target is zero. The existing review order and FSRS due dates are untouched.
3. Chooses the largest whole-word count that fits the remaining time and user ceiling, then checks normal and elevated 14-day FSRS scenarios. The normal case assumes today's due work is completed. The elevated case carries all still-outstanding Reviews (including frozen cards) into tomorrow and applies an uplift from recent independent first answers; without personal evidence the controller uses an explicit conservative sensitivity case. If existing work already exceeds tomorrow's capacity, the planner reports that pressure and admits zero new words.
4. Returns machine-readable reasons such as `due_review_priority`, `future_workload_high`, `new_word_ceiling_reached`, `low_history_confidence`, and `exam_deadline_risk`. A deadline risk never overrides review priority, the safety ceiling, or the future-workload guard.

The FSRS forecast uses disposable cards with the project's already installed `ts-fsrs` 5.4.2, fixed dates and no fuzz. It estimates one new card's marginal Review curve and scales that curve by the candidate count, alongside scheduled future dues and conservative young-card/repeat-load floors. The young-card floor uses the same 21-day scheduled-interval threshold as the snapshot and is combined with due-date forecasts using a maximum, not summed twice. The elevated scenario adds today's outstanding due queue to tomorrow so an unfinished backlog cannot disappear from the forecast. It never writes simulation output to `user_words`, review logs, attempts, BKT evidence or due dates. This remains a bounded forecast, not an individualized forgetting-probability model.

For a deterministic test case, 30 minutes available, 60 due reviews at 16 seconds each (16 minutes), 80 seconds per full new-word path and a ceiling of 20 produce a 90-second buffer and a target of **9 new words**. The estimate allocates 16 minutes to due reviews and 12 minutes to those words; future-load checks may lower the target in other cases.

The legacy admission path remains behind `WORDLOOP_ADAPTIVE_DAILY_BUDGET_V2=false`. It uses the existing static costs and conservative seven-day forecast. Planner errors also fall back to this path so answer submission, Review, grading and progress writes keep working. Setting `learning_settings.budget_enabled=false` stops time-based automatic admission but still enforces the learner's new-word ceiling. A manual 15-minute extension remains available. “Continue one group” adds an idempotent amount based on the user's current full-word and Review costs, then replans under the same due-work and future-load rules; “continue due Review” explicitly enables Review-only work after the budget.

## Time costs and personal calibration

The calibration model is described in [LEARNING_TIME_CALIBRATION.md](LEARNING_TIME_CALIBRATION.md). Answer, grading wait, explanation and feedback are separate. Only validated active answer/feedback/explanation time is used; browser timing pauses while hidden, during network/model waits, and after inactivity. Missing historic time stays null. Production audit on 2026-10-13 found 2,784 attempts with `active_ms` null in every row, so no real historical distribution or backtest is available. Migration `0008_learning_time_prediction_errors.sql` freezes each new task's prediction from only that user's prior local-day histograms, pairs it with one valid finalized actual, and updates compact daily MAE/bias totals idempotently. Insights offers 7/14/30-day actual-time and paired-error windows, with separate full-word lifecycle error. Existing 8/15/30/45/90-second activity costs and 77 seconds per full new-word path remain cold-start assumptions until personal observations arrive.

Each profile is scoped by authenticated `user_id`. A five-second histogram and fixed domain cap produce a robust mean, then shrink it toward the existing activity cost with `n/(n+20)`. The prior strength is provisional because no historical active-time target exists for backtesting. Exact personal activity data is preferred, then a related personal activity, then the existing static cost. A full new-word sample is created only from the same canonical word's validated Pretest, Lesson answer and feedback path; completed group Consolidation is shared across its unique canonical target words once. The daily budget excludes the derived lifecycle aggregate so the same seconds are not counted twice.

The forecast assumptions are intentionally narrower than the full simulators: fixed reproducible seed/date, review-first admission, normal Good and one elevated rating scenario, 7-day and 14-day summaries. They are enough to compare small candidate counts within a Worker request without adding a model or long-running computation.

## Settings, exam goals and counting

Time is the main user setting (20, 30, 45, 60, 90 and 120 minutes are offered). The advanced new-word control remains a ceiling and preserves current settings. An optional exam deadline and coverage target are attached to the selected book; total and covered words use the existing deduplicated book/canonical learner-word model. No deadline means no deadline-pressure calculation. If the sustainable target cannot meet the requested pace, the plan reports `exam_deadline_risk` without secretly raising the ceiling.

The first formal Lesson submission is the introduction event. Queue hydration, Pretest-only exposure, a retry, repeated exercise, old-word repair, dictionary/Capture/Family browsing, and another book label do not count again. A Family micro-course that activates a new canonical word goes through the same service admission and database ceiling check. A V2 row explicitly marked as denied cannot activate; an old frozen Family row with no marker remains usable during rollback only while the same canonical daily ceiling has room. Historical counts use existing first Lesson attempts read-only; the migration does not rewrite old FSRS rows to backfill dates.

Budget stops at a task boundary. The already displayed/frozen task can finish and save normally; an unfinished review remains due. A budget pause is not reported as “all reviews complete” while due cards remain. Frozen sessions and idempotent submission keys continue to govern resume across refreshes and devices. Daily totals follow the learner timezone, defaulting to `Asia/Shanghai`; a frozen prior-day queue remains resumable but cannot admit new words into the old date.

## Database, compatibility and rollback

Neon is the canonical business database; Supabase remains the login provider. Additive migration `0007_adaptive_daily_budget_v2.sql` adds the introduction date/session, daily Review override, optional exam deadline/coverage fields, a 20-word default for new learners, and authenticated planner/goal RPC behavior. Existing user limits and learning rows are retained. `0006_learning_time_calibration_v2.sql` stores per-user time checkpoints and aggregates separately from formal answer/FSRS/BKT records; `0008_learning_time_prediction_errors.sql` adds server-computed prior predictions, paired error summaries, listening-stage classification and bounded 30-day history.

Flags are independent. `WORDLOOP_TIME_CALIBRATION_V2=false` returns static time costs and disables time collection. `WORDLOOP_ADAPTIVE_DAILY_BUDGET_V2=false` selects the untouched V1 allocator and its conservative static admission rule. The V2 allocator is a separate versioned RPC, checks that its user ID matches the authenticated Neon subject, and grants execution only to Neon `authenticated` and `wordloop_admin` roles; it does not assume Supabase's `service_role`. For rollback, turn off the corresponding flag and deploy the compatible application; retain the additive tables and data. Do not roll back by deleting timer observations or changing FSRS/BKT state.

## Existing learning and evidence boundaries

FSRS alone owns review state, due dates, parameters and formal rating. BKT stays on its fixed `fixed-v1` parameters and existing `active`/`shadow`/`off` policy. Tutor Policy still owns the frozen lesson content, and existing DeepSeek generation/grading calls do not receive budget decisions. A telemetry or planning failure falls back without blocking saved answers or review scheduling. The controller adds no model calls and does not tune retention.

Evidence evaluation remains separate: declared skills are normalized, unassessed/assisted outcomes are not converted to independent correctness, and samples require explicit human review before they count as gold. Its metrics do not automatically alter tutoring policy.

## Validation and limits

Planner unit tests exercise cold start, 30-minute allocation, review overload, light Review, future burden, extra time, deadlines, deterministic FSRS simulation and unchanged disposable/live card state. PGlite migration tests also cover the V1 allocator, authenticated cross-user rejection, reserved Reviews, both Family budget-denial paths and legacy Family continuation. The 0008 PGlite checks cover server-owned phase classification, same-day exclusion, retry-safe error updates, canonical full-word error adjustment, 30-day history and preservation of the 0007 Family admission guard. Migrations `0006` and `0007` were applied transactionally to a fresh production clone and production. Migration `0008` was applied and its schema, functions, grants, and unchanged formal-introduction guard verified on isolated Neon branch `br-fancy-dew-azr9k4hx`; production migration and release remain pending. The release record and remaining verification limits are in [LEARNING_TIME_CALIBRATION.md](LEARNING_TIME_CALIBRATION.md).

The active-time data are currently too sparse to claim a successful real-history backtest or learned user costs. Predicted future Reviews are a conservative deterministic scenario rather than a probability-calibrated estimate. Report those limits alongside the UI's cold-start/low-confidence reason instead of presenting a precise forecast as fact.
